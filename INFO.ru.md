# Настройка и эксплуатация QWS

[Основной README и дисклеймер](README.md) · [Русский README](README.ru.md) · [English documentation](INFO.md)

Веб-интерфейс на Nuxt 4 для OrpheusDL с установленным модулем Qobuz.
Ссылки на треки, альбомы, плейлисты и исполнителей → очередь → файлы на сервере.
Есть выбор качества, журнал, отмена заданий, библиотека ZIP-архивов с поиском.

## Docker Compose

```sh
cp .env.example .env
# Заполните ADMIN_USERNAME и ADMIN_PASSWORD в .env.
docker compose up -d --build
docker compose logs -f
```

Откройте `http://localhost:3000` и выберите «Войти», затем используйте `ADMIN_USERNAME` / `ADMIN_PASSWORD`.
OrpheusDL и Qobuz устанавливаются автоматически при сборке образа; вручную клонировать их не нужно.
Контейнер работает от непривилегированного пользователя. Внутри — Python, FFmpeg и Node.js.

Для сети с собственным доверенным CA поддерживается BuildKit secret:
`docker build --secret id=build_ca,src=/path/to/organization-ca.pem -t qws-dl .`.
CA добавляется в хранилище доверия; проверки TLS и подписей пакетов остаются включёнными.

Файлы сохраняются в том `downloads`, история и сессия Qobuz — в `app-data`.
`docker compose down` сохраняет тома; **`docker compose down -v` удаляет коллекцию и настройки**.
Чтобы скопировать коллекцию: `docker compose cp qws-dl:/downloads ./saved-downloads`.
После изменения `.env`: `docker compose up -d --force-recreate`.
По умолчанию порт доступен только на localhost. Для удалённого доступа настройте TLS reverse proxy;
`WEB_BIND` определяет адрес привязки, `WEB_PORT` — порт на хосте. Не запускайте несколько реплик на общих томах.

## Локальная разработка

### Подпуть nginx `/dl/`

Блоки `location` для существующего `server {}` находятся в [deploy/nginx-dl.conf](deploy/nginx-dl.conf).
Добавьте `NUXT_APP_BASE_URL=/dl/` в `.env` и пересоберите приложение после обновления кода:
`docker compose up -d --build`. Конфиг предполагает nginx на хосте и приложение на `127.0.0.1:3000`.
В `proxy_pass` нет завершающего `/`: приложение должно получать полный путь `/dl/...`.
Если nginx работает в общей Docker-сети, замените upstream на `http://qws-dl:3000`.
Проверьте конфигурацию командой `nginx -t`, затем перезагрузите nginx.
Префикс применяется также к API, ресурсам, ссылкам и cookie; `/api/health` становится `/dl/api/health`.
Поддерживаются `/`, `/dl`, `/dl/` и вложенные пути вроде `/music/dl/`.
`NUXT_APP_BASE_URL` — путь внутри сайта, например `/dl/`, а не полный адрес с доменом.
После первого обновления кода изменение только этого параметра не требует пересборки:
`docker compose up -d --force-recreate`. При запуске без Docker перезапустите `npm start` или `npm run dev`.

### Запуск без Docker

Нужны Node.js 22.12+ (или 24), Python 3.10+ с `venv`, Git и FFmpeg в `PATH`.
На Debian/Ubuntu: `apt-get install python3 python3-venv git ffmpeg`.

```sh
npm ci
npm run setup:orpheus
cp .env.example .env
# Заполните .env.
npm run dev
```

Nuxt читает `.env` в режиме разработки. Production:

```sh
npm run build
npm start
```

`npm start` загружает `.env` средствами Node.js. При прямом вызове `.output/server/index.mjs`
переменные должен передать процесс запуска. В Compose их передаёт `env_file`.
`npm run setup:orpheus` можно запускать повторно; изменённые отслеживаемые файлы upstream он не перезаписывает.
Python-зависимости закреплены в `requirements-orpheus.lock`, JavaScript-зависимости — в `package-lock.json`.

## Настройки `.env`

| Переменная                          | Назначение                                                                                                                               |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD`  | Логин администратора (по умолчанию admin) и пароль длиной 10–256 символов                                                                |
| `USER_INVITE_LIMIT`                 | Число регистраций по коду обычного пользователя: 0–10000, по умолчанию 1; администратор без лимита                                       |
| `DOWNLOAD_RETENTION_HOURS`          | Срок хранения по умолчанию после завершения: целое число от 1 до 24 часов, по умолчанию 24                                               |
| `DOWNLOAD_QUALITY`                  | `hifi` (до 192 кГц / 24 бит), `lossless` (44,1 кГц / 16 бит), `high` (MP3 320)                                                           |
| `ORPHEUS_DIR`, `PYTHON_BIN`         | Путь к установленному OrpheusDL и Python его виртуального окружения                                                                      |
| `DATA_DIR`, `DOWNLOAD_DIR`          | Каталоги истории и загруженных файлов                                                                                                    |
| `JOB_TIMEOUT_SECONDS`               | Лимит времени одного задания, по умолчанию 7200 секунд                                                                                   |
| `WEB_BIND`, `WEB_PORT`              | Только Compose: адрес и порт на хосте                                                                                                    |
| `NUXT_APP_BASE_URL`                 | Базовый путь приложения: `/` по умолчанию, например `/dl/`                                                                               |

Относительные локальные пути считаются от корня проекта. В Compose пути переопределены на контейнерные.
Учётные данные Qobuz не передаются в браузер и не включаются в Docker-образ. При загрузке Python записывает их в
конфигурацию OrpheusDL с правами 600; том `app-data` и локальный `.runtime` содержат приватные данные.
Журналы ограничены по размеру, URL и значения секретов скрываются. Не публикуйте `.env` и тома.
Статус «Настроено» проверяет наличие параметров, а не успешную авторизацию в Qobuz.
Параметры веб-клиента приложение получает автоматически через `qobuz-dl`.
Авторизация Qobuz выполняется только через вход на сайте из настроек администратора.
Используйте сервис для контента, к которому у вас есть разрешённый доступ.

## Аккаунты и приглашения

Задайте в `.env` `ADMIN_USERNAME=admin`, приватный `ADMIN_PASSWORD` длиной 10–256 символов
и `USER_INVITE_LIMIT=1`. Пересоздайте контейнер. Администратор создаётся при запуске;
изменение его логина или пароля в `.env` обновляет тот же аккаунт и завершает его сеансы.
Код приглашения сохраняется. Логины: 3–32 латинские буквы/цифры, точки, дефисы и подчёркивания,
без учёта регистра.

Первый экран запрашивает приглашение. Существующие пользователи и администратор выбирают
«Войти». После проверки кода приглашённый выбирает логин и пароль. Без кода регистрация закрыта.
В настройках каждого пользователя — свой код и оставшееся число приглашений. Код используется
до исчерпания лимита; удаление приглашённого аккаунта не возвращает приглашение.
`USER_INVITE_LIMIT` — целое число 0–10000, по умолчанию 1; применяется после перезапуска.
У администратора лимита нет. Блокировка/удаление владельца отключает его код, но не аккаунты приглашённых.

В разделе «Пользователи» администратор видит аккаунты, пригласивших и использование приглашений,
может блокировать/разблокировать, сбрасывать пароли и удалять аккаунты с подтверждением.
Администратора нельзя удалить или заблокировать через интерфейс; его данные меняются через `.env`.
Обычный пользователь меняет свой пароль в настройках. Смена/сброс пароля, блокировка, удаление
и выход отзывают соответствующие сеансы. Блокировка и удаление останавливают активные задания;
оставшиеся файлы удаляются по прежнему сроку хранения. Регистрация не позволяет назначить себе роль администратора.

Пользователь видит и скачивает только собственные задания и ZIP; доступ проверяется на сервере.
В обычной библиотеке администратора — свои и старые загрузки. Отдельный раздел «Хранилище»
показывает архивы всех пользователей и позволяет удалить их после подтверждения, без доступа
к скачиванию чужих архивов. Удаление сразу освобождает каталог задания и закрывает новые запросы
на скачивание; история остаётся с отметкой удаления. Во время загрузки или архивации удаление
запрещено: сначала отмените загрузку и дождитесь завершения упаковки.
Учётные данные Qobuz остаются общей настройкой сервера. Аккаунт приложения не является аккаунтом или подпиской Qobuz.

Аккаунты и scrypt-хеши паролей с индивидуальной солью хранятся в `DATA_DIR/users.json` (права 0600).
Случайные сеансы действуют 12 часов; в файле хранятся только хеши токенов. Cookie — HttpOnly,
SameSite=Strict, с путём приложения; при HTTPS используется Secure. Храните том приватно и делайте
резервную копию `DATA_DIR`. Поддерживается один Node-процесс/реплика. Общий лимит попыток авторизации
и управления аккаунтами ограничивает нагрузку на хеширование без доверия заголовкам прокси.

При обновлении старый `WEB_PASSWORD` временно используется как пароль администратора,
если `ADMIN_PASSWORD` не задан; логин — `admin` или значение `ADMIN_USERNAME`.
Перейдите на новые переменные. Старые cookie с общим паролем больше не подходят.
Пароль должен соответствовать новому ограничению длины. Старые загрузки при запуске упаковываются в ZIP с проверкой перед удалением исходников.

## Очередь и ограничения

Один Python-процесс обслуживает очередь по порядку, чтобы не повредить сессию OrpheusDL.
Отмена останавливает группу процессов; уже сохранённые файлы упаковываются в ZIP.
После перезапуска ожидающие задания продолжаются, прерванное задание получает статус ошибки:
при необходимости добавьте его ссылку заново. История хранит последние 200 записей и все задания с ещё не истёкшим сроком хранения, очередь — до 50 активных.
Каждое задание пишет во временный каталог; после упаковки в нём остаётся только ZIP. Библиотека показывает сохранённые архивы.
Успешное задание означает завершение CLI без ошибок, обнаруженных в выводе;
OrpheusDL управляет метаданными, доступностью треков и выбором фактического качества.
Отдельные ошибки треков считаются ошибкой задания, даже если upstream возвращает код 0.
Поиск треков Qobuz доступен в разделе «Загрузки → Поиск Qobuz» через API модуля.

## Проверки

```sh
npm test
npm run test:python
npm run typecheck
npm run build
docker compose config --quiet
```

После сборки и установки Python-окружения: `npm run test:integration`.
Этот тест запускает production-сервер и проверяет вход, очередь, Python-мост, выдачу файлов,
ошибку отдельного трека, отмену и восстановление истории. Вместо сетевого Qobuz используется локальный стенд.

На момент проверки `npm audit` сообщает 11 high в цепочках инструментов сборки (`braces`, `node-forge`).
`npm audit fix` их не устраняет в текущих upstream-версиях. Эти пакеты отсутствуют в собранном
production-сервере `.output`; для развёртывания используйте production-образ, а не dev-сервер.

`/api/health` проверяет HTTP-сервер, не Qobuz. Проверка реальной загрузки:
заполните учётные данные, добавьте доступный вашему аккаунту трек, дождитесь завершения,
откройте библиотеку и скачайте файл. Без действительных данных Qobuz эту проверку выполнить нельзя.

Upstream закреплены на коммитах в `scripts/install-orpheus.sh`:
[OrpheusDL](https://github.com/OrfiTeam/OrpheusDL) и
[OrpheusDL Qobuz](https://github.com/yarrm80s/orpheusdl-qobuz).
Исходники upstream не включены в этот репозиторий, устанавливаются в `.runtime` или `/opt/runtime`.

## Вход в Qobuz и автоматическое обновление сессии

Войдите в QWS как администратор и откройте **Настройки → Qobuz → Войти в Qobuz**.
Введите email и пароль на сайте Qobuz и пройдите проверку, если её запросит сервис.
После входа вы вернётесь в QWS. Копировать токен и устанавливать браузер на сервер
не нужно. В `.env` больше нет отдельных настроек авторизации Qobuz.

Старые `QOBUZ_AUTH_MODE`, логин/пароль, ручные токены и ключи приложения игнорируются:
их можно удалить из своего `.env`. Уже сохранённая OAuth-сессия продолжит работать
после обновления; удалять тома или историю не нужно.

Сессия хранится в `DATA_DIR/qobuz-session.json` с правами `0600`, в Docker — в томе
`app-data`. Поиск и загрузки получают её приватно; браузеру токен не отправляется.
Повторный вход заменяет общий аккаунт Qobuz для сервера. Нужна подходящая подписка.

Раз в минуту фоновая задача проверяет необходимость обновления: через 30 минут
после последнего успешного обновления или за пять минут до истечения, если JWT
содержит срок действия. Срок из JWT используется только для планирования, не как
доказательство авторизации. При обновлении проверяются аккаунт, подписка и подпись;
возвращённый Qobuz токен сохраняется атомарно после запроса `user/login` с текущей сессией.
Это попытка продления средствами сервиса, а не гарантия бессрочного входа: отдельного
refresh-секрета для восстановления отозванной сессии у нас нет. Если Qobuz не продлит
срок или потребует новую проверку, понадобится снова войти на его сайте.

При сетевой ошибке сессия сохраняется, повтор — через пять минут. При отказе
авторизации приложение показывает необходимость повторного входа и прекращает
фоновые попытки до нового входа администратора. Параллельные обновления объединяются;
старый запрос не перезапишет новый аккаунт. После перезапуска сроки сохраняются,
а старые файлы сессии из двух полей обновляются при запуске.

Вход начинает только администратор. Одноразовый state действует десять минут и
связан с отдельной HttpOnly SameSite=Lax cookie и сессией администратора. Основная
cookie QWS остаётся SameSite=Strict. После перезапуска во время входа начните снова.
Для `/dl/` задайте `NUXT_APP_BASE_URL=/dl/`, сохраните Host/X-Forwarded-Proto и
используйте [конфиг nginx](deploy/nginx-dl.conf) с отключённым access-логом callback.
При других прокси примените аналогичные правила журналирования. Серверу нужен
HTTPS-доступ к `play.qobuz.com`, `www.qobuz.com` и адресам медиа/обложек. Проверки
браузера выполняются на сайте Qobuz.

Прежний прямой парольный API перестал работать после изменений Qobuz в апреле
2026 года: [qobuz-dl #329](https://github.com/vitiko98/qobuz-dl/issues/329),
[OAuth #331](https://github.com/vitiko98/qobuz-dl/pull/331),
[streamrip #954](https://github.com/nathom/streamrip/issues/954).

## Названия загрузок

В очереди и имени ZIP показываются исполнитель и название из метаданных OrpheusDL.
Название появляется после получения метаданных; до этого видны тип материала и ID Qobuz.
Новые аудиофайлы называются «Исполнитель - Название», внутри альбомов и плейлистов — с номером трека.
Кириллица в именах ZIP сохраняется. Существующие файлы не переименовываются; для старых
заданий название берётся из папки альбома или имени единственного аудиофайла, если это возможно.

## Поиск песен в Qobuz

Откройте «Загрузки → Поиск Qobuz», введите название песни или исполнителя и нажмите
«Найти». В результатах видны название/версия, исполнитель, альбом и длительность.
Отметьте треки, выберите качество и срок хранения, затем добавьте их в очередь.
Недоступные для скачивания треки выбрать нельзя. «Показать ещё» загружает следующую
страницу: по 20 результатов, максимум 1000; за одно действие можно выбрать до 50 треков.
Каждый выбранный трек становится отдельным заданием и ZIP своего пользователя.
При ошибке или заполнении очереди добавленные треки отмечаются, остальные остаются
выбранными для повторной попытки. Уход со страницы поиска останавливает оставшиеся добавления.

Поиск доступен авторизованным пользователям и использует текущие настройки Qobuz:
`web`, `token` или `mobile`. Дополнительные переменные или ключи не нужны.
Поиск читает метаданные каталога и не изменяет настройки/сеансы загрузчика.
Запрос отправляется по кнопке, ограничен 45 секундами; одновременно разрешены один
поиск на пользователя и два на весь сервер. Ответы API и секреты в ошибках не раскрываются.
Доступность скачивания и фактическое качество определяются Qobuz и настроенным аккаунтом.

## ZIP-архивы и срок хранения

На форме загрузки выберите срок от 1 до 24 часов. По умолчанию он задаётся
через `DOWNLOAD_RETENTION_HOURS=24`. Отсчёт начинается после завершения задания,
в том числе ошибки или отмены, если остались частичные файлы.

После остановки загрузчика очередь автоматически создаёт ZIP64, проверяет его содержимое
и контрольные суммы CRC, затем удаляет исходники, служебные метаданные и временные файлы.
В папке задания остаётся только ZIP. Скачивание отдельных исходников через API закрыто.
Во время упаковки виден статус «Создаётся ZIP». Частичные файлы после ошибки или отмены
также архивируются. Аудио не пережимается; имена, папки, обложки и дополнительные файлы сохраняются.
Символические ссылки не включаются в архив и удаляются без перехода по ним.
Для упаковки временно нужно дополнительное место под ZIP до удаления исходников.

При ошибке упаковки или очистки исходники по возможности сохраняются. В интерфейсе появится
ошибка и кнопка «Повторить архивацию» / «Повторить», без повторной загрузки из Qobuz.
Маркер завершённой упаковки защищает полный ZIP от перезаписи оставшейся частью исходников,
если очистка прервалась. При запуске сервер продолжает незавершённую упаковку и переводит
старые непросроченные загрузки в ZIP. Посторонние каталоги без записи задания не изменяются.

По окончании срока сервер удаляет папку задания с ZIP и остатками после неудачной очистки.
Новые запросы к просроченным файлам блокируются; запись в истории сохраняется.
В интерфейсе отображаются время истечения и отметка удаления.
Если удалить файлы не удаётся, интерфейс показывает ошибку прав доступа,
сервер повторяет попытку, а выдача просроченных файлов остаётся заблокированной.

Очистка выполняется работающим сервером и при запуске. Если сервер выключен,
просроченные файлы удаляются при следующем старте; для удаления по расписанию
сервер должен работать. Старым записям назначается срок 24 часа от времени завершения.
Конфигурация и посторонние каталоги, вручную помещённые в downloads, не удаляются.

## Ограничения и защита загрузок

JSON-запросы ограничены 64 КиБ, включая chunked-передачу. Для авторизации действует
лимит 30 запросов в минуту отдельно для каждой операции и клиента; проверка
приглашений не расходует лимит входа. Одновременно выполняется не более восьми
операций хеширования паролей. После чтения тела защищённого запроса сессия
проверяется повторно, поэтому блокировка аккаунта отменяет отложенное добавление.

За reverse proxy включайте `TRUST_PROXY=true` только если прямой доступ к порту
приложения закрыт, а прокси перезаписывает `X-Real-IP` реальным адресом клиента.
Пример nginx уже перезаписывает этот заголовок. По умолчанию используется адрес
непосредственного соединения, без доверия пользовательским заголовкам.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MAX_USER_JOBS` | 10 | Активные задания одного аккаунта |
| `MAX_JOB_BYTES` | 10737418240 | Бюджет скачивания задания, 10 ГиБ |
| `MAX_USER_BYTES` | 21474836480 | Бюджет сохранённых файлов аккаунта, 20 ГиБ |
| `MIN_FREE_BYTES` | 1073741824 | Резерв свободного места, 1 ГиБ; допустим 0 |

Общий предел очереди — 50 активных заданий. Создание ограничено 30 заданиями
в минуту на аккаунт; сохраняется не более 200 неистёкших заданий одного аккаунта
и 2000 на сервер. Записи без файлов за пределами последних 200 удаляются из
истории; записи с файлами сохраняются для корректной очистки. Сохранение журнала
объединяется с задержкой до 500 мс, изменения статусов записываются сразу.

Размер проверяется при потоковом скачивании и раз в секунду для папки воркера.
Эти проверки не заменяют системную квоту файловой системы: сторонний процесс
может увеличить файл между проверками. До упаковки проверяется место для ZIP,
а исходники удаляются только после успешной проверки архива. Исправный готовый
архив не занимает воркер при повторном запросе архивации.

`scripts/worker_safety.py` применяет защиту при запуске закреплённого OrpheusDL:
проверка TLS обязательна, запросы имеют тайм-аут, HTTP-ошибки не записываются как
аудио, имена и пути ограничены папкой задания. Временные файлы находятся внутри
`.qws-work` задания и не входят в ZIP. Доверенные CA задаются через
`REQUESTS_CA_BUNDLE`; отключение проверки сертификатов не поддерживается.

Плейлисты и альбомы исполнителя загружаются постранично с проверкой полноты,
изменения коллекции и повторяющихся элементов. Коллекции свыше 10000 элементов
отклоняются явно. Неиспользуемый уязвимый `protobuf` исключён из Python-зависимостей.
Оставшееся предупреждение инструментария Nuxt описано в `SECURITY.md`.

## Безопасная диагностика сессии

```sh
docker compose run --rm --no-deps --entrypoint node qws-dl /app/scripts/diagnose-qobuz.mjs
# Без Docker:
npm run diagnose:qobuz
```

Диагностика использует только сохранённую OAuth-сессию. В JSON остаются наличие
сессии, фиксированные этапы, HTTP-статусы и категория результата. Email, пароль,
токены, ключи, URL, тела ответов и тексты исключений не выводятся. Сессия и настройки
не меняются, аудио не скачивается. Успех означает, что текущая сессия и подпись
принимаются сейчас, но не гарантирует длительность её действия. Код завершения:
0 при успехе, 1 при ошибке. JSON можно прислать для диагностики. Прежние режимы
входа и опция сравнения парольных запросов удалены.
